# Qwen3.8 DFlash2：验证耗时、融合 GDN 与 C4/C8 复测

日期：2026-09-30。单张 NVIDIA A800-SXM4-80GB，K=7，验证块长 4，
固定 micro-batch 4。基于本地 checkpoint `ae7f87e` 的共同 target 数值路径。
实现 checkpoint：`dfc47c9`。42 个生产/benchmark 文件在统一 CRLF/LF 后，
本地与远端全部哈希一致；原始字节哈希仍按每轮 manifest 保存。
实验功能默认关闭，使用 `--vectorized-target-numerics --fused-gdn-target` 开启。

测试负载为固定 seed `20260907` 的 short 请求，输出固定 64 token，
`ignore_eos=True`；C4 每轮 16 请求，C8 每轮 32 请求。每个模式先预热
1 请求，随后开始计时；模型加载与预热不计入端到端吞吐。
两个模式均启用相同的新 target 数值路径；比较不要求复现旧核的历史输出。
EOS 语义另外由 tiny-model 测试覆盖，不由固定长度吞吐实验覆盖。

## 结论

**适用范围更正：本报告的 128 输入/64 输出只覆盖短请求，其 prefill 占比
过高，不足以判断长输出投机解码收益。以下“未证明稳定加速”仅限该短请求
负载，不能作为 DFlash2 整体性能结论。按用户要求补测 4096 输出，保持请求输入
和模型实现不变，并分别报告解码阶段与端到端吞吐。**

已完成 GDN 融合递推、精确前缀恢复验证、算子归因与 C4/C8 各三轮配对。
六轮合计 **144/144 请求、9216/9216 输出 token** 在同轮两模式间完全一致；
同并发量各轮 target-only 输出也完全一致。最终全量测试 **248 passed、2 skipped**。
采样显示 GDN GPU 耗时明显下降，但 **C4/C8 均未证明稳定端到端加速**：

| 并发 | 三轮 DFlash2/target 吞吐比 | 比值均值 | 样本标准差 | DFlash2 显存峰值 GiB |
|---|---|---:|---:|---:|
| C4 | 1.0028、0.9915、0.9741 | 0.9895 | 0.0144 | 55.613 |
| C8 | 1.0061、1.0919、0.9556 | 1.0179 | 0.0689 | 57.043–57.065 |

标准差描述这三次观测的波动，不是置信区间。新核默认关闭；新旧 target
数值路径在已比较的 C4 请求中有 8/16 输出不同，尚未评估质量影响。
当前服务器只有一张 GPU，TP=2 和 C16/C32 双卡验证仍未完成。

## 验证阶段采样

在旧核 C4 的第 21、22 次 verifier 调用采样，均为 4 个请求、每请求
最多 8 个待评分位置。两次调用因接受情况分别执行两个块、一个块。
使用 PyTorch profiler 保存 CPU 事件和 Chrome trace，然后通过 CUDA
runtime/driver 的 correlation ID 把 GPU 核分配给最内层模型阶段。
该处理包含 Triton 自定义核；仅依赖 PyTorch 的算子 CUDA self time 表
会漏掉自定义投影核。分类互不重叠，以下是 GPU 核与复制的持续时间之和。

| 阶段 | 调用 21 毫秒 | 调用 22 毫秒 | GPU 时间占比范围 |
|---|---:|---:|---:|
| 线性投影 | 88.97 | 49.34 | 42.7%–46.3% |
| GDN 递推及其他逐元素计算 | 52.15 | 31.79 | 27.1%–27.5% |
| verifier 其余工作与缓存整理 | 15.67 | 12.70 | 8.2%–11.0% |
| LM head | 11.87 | 6.01 | 5.2%–6.2% |
| full-attention 核与缓存（含 matmul，不含投影） | 10.75 | 6.53 | 5.6%–5.7% |
| 全部 GPU 核与复制合计 | 192.23 | 115.42 | 100% |

GDN 递推及逐元素阶段分别启动约 6720、3360 个 GPU 核/复制。
CPU 采样也显示大量小算子启动和缓存操作。Profiler 会显著扰动耗时，
上述两次采样不能用作吞吐收益测量，正式性能实验不启用此 profiler。
全阶段计时另用运行边界的 wall time；CPU 时间与 GPU 时间存在重叠，不能相加。

融合后采样位于 `c4_gdn_fused_profile_20260930/verify_6.json`，仍为
4 个请求并执行两个 4-token 块。投影核次数同为 992，GPU 投影时间
88.94 ms，与旧采样 88.97 ms 接近。GDN 剩余逐元素操作 6.35 ms，
融合递推及其复制 3.51 ms，合计 **9.86 ms**；旧采样同类为 52.15 ms，
减少约 **81.1%**。该部分 GPU 核/复制数从 6720 降至 1824。
全 GPU 算子持续时间从 192.23 ms 降至 150.27 ms，减少约 21.8%。
这是一组结构相同、请求内容不同的诊断样本，不是冻结输入的配对吞吐测量。
融合后投影占 GPU 时间约 **59.2%**，缓存整理等 verifier 其余工作约 10.4%，
LM head 约 7.9%；优化优先级应依据这些测量，而不是假定 attention 最大。

同两次采样中的 CPU self time（含 profiler 扰动）如下，不能直接当作
未采样运行的墙钟占比：GDN 递推/逐元素及融合包装合计 199.61 → 96.88 ms；
verifier 其余工作/缓存整理 187.32 → 187.43 ms；投影调度 100.57 → 97.21 ms；
attention 核/缓存与 matmul 调度合计 93.58 → 93.12 ms。
全部 CPU self time 为 755.97 → 630.91 ms。后续需同时减少投影成本与
Python/PyTorch 缓存整理调用，不能仅根据 GPU 算子占比解释整个 verifier。

## 实现与正确性

新增 `qwen35_gdn.py`：每个 GPU program 持有一个请求、一个 head、
一组 value 列的 FP32 状态，按因果顺序处理候选位置。块内仍存在 GDN
状态依赖，但完整矩阵不再在每个位置反复写回并由许多 PyTorch 小算子读取。
投影继续整块计算，target-only decode 与 verifier 使用相同递推核。

前缀恢复只记录每位置的 decay、key、delta、conv state；不保存每个位置
的完整 recurrent-state 矩阵。临时 delta 缓冲的大小为 O(B×T×H×Dv)，
持久状态仍为 O(B×H×Dk×Dv)。临时缓冲计入 CUDA 分配峰值，保留的记录
计入现有 `transaction_linear_update_bytes`。

为保持精确缓存语义，单步与块验证使用同一编译布局、相同 FP32 舍入边界，
并保留相同的小 delta 写出。实验过程中发现省略 decode 的 delta 写出会
改变编译器归约布局，即使差异很小也会破坏精确前缀恢复；该失败原型的
测试日志保留，最终路径没有放宽状态比较容差。

新增 CUDA 测试覆盖独立 FP64 公式参考、BF16/FP32、真实 head dimension
128 与 tiny dimension 4、单步/3/4/8-token 分块、所有前缀精确恢复、
接受长度 0..7、异长 batch、EOS 截断、异常 rollback。14 项均通过。
初次全量回归为 247 passed、2 skipped；另补充计时包装器生命周期回归。
最终执行 `PYTHONPATH=src .venv/bin/python -m pytest -q tests`，
**248 passed、2 skipped，40.31 秒**。日志为
`logs/qwen38_dflash2_perf/final_tests_scoped_20260930.log`。
最初未指定 tests 目录的命令误收集 results 中保留的旧测试副本，发生
import-file mismatch；该收集失败日志也保留，未删除历史材料来规避问题。

| 轮次 | target-only tok/s | DFlash2 tok/s | 吞吐比 | target decode 秒 | verify 秒 | proposal+commit 秒 | DFlash2 峰值 GiB |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 5.7442 | 5.7602 | 1.0028 | 21.728 | 19.611 | 4.118 | 55.613 |
| 2 | 5.6109 | 5.5634 | 0.9915 | 23.050 | 20.455 | 4.506 | 55.613 |
| 3 | 5.6640 | 5.5175 | 0.9741 | 22.444 | 20.697 | 4.554 | 55.613 |

配对吞吐比均值 **0.9895**，范围 0.9741–1.0028，**C4 无稳定端到端加速**。
三轮接受长度 0..7 直方图完全相同：72、56、44、30、14、11、12、44。
三轮 verifier 计数也相同：85 次调用、150 个实际模型块，执行 1423 个
请求-token 位置，跳过 747 个请求-token 位置。verifier 首拒位置 0..6
直方图为 68、54、43、27、12、8、12，完整通过其验证候选的请求周期为 59。
它与提交后的接受长度直方图口径不同：临近输出长度上限时，proposal 会截短。
并行路径的 `avoided_model_steps` 当前固定记为 0，是未实现的统计项，
不能用它断言没有跳过完整块。实际模型块数与请求-token 跳过数可用。
部分请求结束时同组其他请求可能仍需固定形状块，因此跳过位置数也不能
直接等同于 GPU 工作量同比下降。
target-only prefill 范围 155.60–158.40 秒，DFlash2 prefill 为
153.45–159.90 秒。target-only TTFT p50 为 38.18–39.13 秒，DFlash2 为
18.71–19.89 秒；TPOT p50 分别为 0.0909–0.0958 秒、0.3758–0.3922 秒。
这些闭环请求延迟包含其他请求的 prefill 阻塞与不同的完成时序，不能直接
解释为 prefill 算法加速；两模式的 prefill 实现相同。

首轮 break-even：普通 decode 21.73 秒，投机 verify+proposal+commit+sample
合计 23.73 秒。若接受情况、其他阶段及预填充保持不变，verify 必须降到
约 **17.61 秒**（比当前再降约 **10.2%**）才可使 decode 阶段持平。
当前端到端略快与两模式预填充相差 2.15 秒有关。旧核与新核实际执行的
target 模型块数分别为 145、150；新核没有通过减少模型块数获得这轮
verify 时间下降。新核接受长度直方图总计 283 个请求周期，平均每周期
输出 `(725+283)/283 = 3.56` 个 token，但整个 speculative 周期仍有
草拟、验证、提交和不满 batch 的成本，因此大于 1 个 token 不保证加速。

以首轮为例，1008 个非 prefill 输出在普通 C4 decode 中需要 252 次
目标模型单步，约 86.2 ms/次；DFlash2 的 verifier 执行 150 个目标模型块，
约 130.7 ms/块。验证本身确实少花约 2.12 秒，但 proposal+commit 约需
4.12 秒，把这部分节省抵消。每个请求周期输出 3.56 个 token，不能直接
当作整个 C4 batch 的 3.56 倍加速。

三轮 C4 显存 trace 的 `hybrid_transaction_snapshot_state_bytes` 均始终为 0。
小型前缀更新记录峰值为 148,893,696 bytes（约 142 MiB），事务原始状态
约 631 MiB；后者每请求保存一次，不随 K 复制。C8 已完成轮次的前缀记录
峰值为 319,057,920 bytes（约 304 MiB），完整逐位置快照仍为 0。

## 预填充瓶颈

`Qwen35ForCausalLM.forward_with_cache` 对输入 token 循环调用完整
`forward_cached_step`，当前 prefill 路径尚未按时间维合批。新融合开关只
作用于 decode/verify/replay，两个模式继续使用相同的旧 prefill 实现。
当前 short 负载 prefill 占端到端约 86%–88%，是整体耗时的主要来源。
因此即使验证更快，端到端收益也很小，并容易受 prefill 运行波动影响。
预填充时序还会影响其他在线请求的 TTFT/TPOT，延迟与吞吐必须一起解读。

## 算法边界

[官方 DFlash2 说明](https://inco.ai/blog/dflash2/)采用整块并行草拟，
由 target 对候选块做因果验证。本轮 Mini-vLLM 的性能设置使用额外的
4-token 分块执行策略，首次拒绝后跳过后续块；全部接受时会执行第二块。
整块 K+1 单次验证路径也存在，但不能把本轮两块配置称作一次完整
8-token target 前向。GDN 的因果递推在融合 GPU program 内执行，
投影按块合批；本轮没有实现并行 scan，也没有实现 TP=2。
