# Qwen3.8 + DFlash2：4K 输出配对测试

日期：2026-10-07。状态：三轮诊断配对及一轮关闭细分 profiling 的控制配对均已完成并通过审计。当前 C4／4K 负载仍未获得加速。

## 目的与范围

按用户要求将正式输出长度设为每请求 4096 tokens。此前约 128 输入、
64 输出的短请求结果不能代表长输出投机收益。本轮保持模型和验证实现不变，
单独测量长输出条件下的端到端吞吐、解码阶段耗时、延迟、接受率及显存。
用户随后明确选择自然需要长输出的代码／推理任务，替换原来的短提示。

## 配置

- 单张 A800-SXM4-80GB，C4、K=7、验证块长 4、micro-batch 4。
- 每轮 4 个完整代码／推理任务，输入长度依次 187、194、190、201 tokens；各输出 4096。
- 每轮是单批 4 个请求，不在请求完成后补入新请求；需报告收尾阶段并发下降，
  不把该配置直接等同于持续满载的在线服务吞吐。
- 使用模型聊天模板，模板默认包含 xhigh reasoning 设置。输出计数包括推理 token。
  完整任务和模板原样保留，不按固定输入长度截断。
- 三轮配对，同样的输入与 seed；顺序为 target/DFlash、DFlash/target、target/DFlash。
- greedy、ignore_eos=True；每轮每模式共 16,384 输出 tokens。
- 两模式均启用共同 vectorized target 数值路径与融合 GDN。
- 两模式均开启 `--lightweight-live-stats`：运行中只读取当前计数，计时结束后
  通过工作线程命令导出完整历史。接受历史不截断，逐 token 输出日志完整保留。
- 三轮诊断矩阵开启 `--profile-dflash2-stages` 与 `--memory-trace`。
  细分 profiling 在 draft 前向及上下文投影处插入 GPU 同步，会产生额外开销。
  因而三轮结果首先代表这一诊断配置；矩阵结束后补充同输入、仅关闭细分
  profiling 的一轮配对控制，检查同步测量对结论的影响。显存追踪保持开启。
- 在线预热为 4 个请求、各 64 输出 tokens；正式请求仍为 4096。
  引擎另有最大模型窗口的初始化预热。加载和两类预热均排除在正式计时之外。
- 长窗口会改变固定 attention padding；严格比较针对本轮两模式，
  不要求与 64 输出配置的历史序列前缀相同。
- 固定长度合成负载用于性能与实现一致性检查，不代替自然 EOS 或质量评测。

### 原短提示的 4K 诊断

`c4_decode4096_r0_20261007` 完成 target-only 四请求、16,384 输出 token：
26.4037 tok/s，总耗时 620.519 秒，其中 prefill 37.823 秒、target decode
393.988 秒，剩余 188.708 秒在模型调用之外，包含统计、输出投递及调度等。
发现实时快照每步对全部历史记录调用 dataclasses.asdict，总工作量随步数
呈二次增长；4095 条历史的独立 CPU 快照中位耗时约 56.23 ms，1024 条
约 14.07 ms。轻量计数快照低于 0.001 ms，不序列化历史。不能把剩余的
188.708 秒全部归因于统计，但已确认这是显著的测量干扰。

此轮四请求首次 EOS 位置分别为 1104、313、无、985；其中两条有大量低多样性
续写。该短提示强制 4K 负载不适合充当自然长回答的主要性能证据。已保存
target 完整结果，在 DFlash2 初始化期间终止该实验进程组，没有形成有效配对。
所有旧文件保留；用户明确同意改用自然长任务。

### 新任务首个 target-only 观测

首轮四个新任务各输出 4096 tokens，均未出现 EOS；各请求末尾 256 tokens
的不同 token 数分别为 126、85、142、119。target-only 吞吐 37.5337 tok/s，
总耗时 436.515 秒，其中 prefill 58.947 秒、target decode 376.570 秒，
其余约 0.998 秒。解码占总耗时约 86.3%；同输入配对见下节。
输入任务已更换，因此不把与旧短提示诊断的全部耗时差异归因于统计修复。

### 自然长任务首轮配对

原始 JSONL 独立审计通过：4/4 请求、16,384/16,384 输出 token 严格一致。
target-only 37.5337 tok/s，DFlash2 33.8679 tok/s，吞吐比 0.9023。
两模式均无提前 EOS。DFlash2 峰值分配显存 59.490 GiB，完整逐位置状态快照为 0，
小型前缀记录峰值 170,164,224 bytes。

target-only prefill/decode 为 58.947/376.570 秒；DFlash2 prefill 58.229 秒、
verify 350.264 秒、proposal 27.889 秒、commit 47.016 秒、sample 0.021 秒。
DFlash2 模型阶段外耗时仅约 0.344 秒。当前差额主要已落在实际投机执行阶段，
不能再归因于短输出 prefill 占比或全历史统计开销。

接受 11,202/36,229（30.92%）。接受长度 0..7 直方图为
1319、1230、875、587、362、228、166、411，合计 5178 个请求周期，
平均每周期输出 3.16 tokens。完整接受历史包含 1345 个 engine decode 步，
与实际 decode 步数一致。1272/1345 步（约 94.6%）保持 4 请求并发；
收尾阶段分别有 3 请求 3 步、2 请求 11 步、1 请求 59 步。

普通 decode 需 4095 个单步；verifier 执行 2183 个模型块，实际执行
25,372 个请求-token 位置、跳过 16,035 个请求-token 位置。
验证节省约 26.31 秒，但 proposal 单独已需 27.89 秒，commit 又需 47.02 秒。
若其余成本和接受分布保持不变，verify 需降至约 301.64 秒（再降约 13.9%）
才能让 decode 阶段持平。该阈值只比较已计时阶段。

上述 coordinator / target 阶段统计是主机墙钟分段，不是独立 CUDA kernel 时间。
自然同步和细分 profiling 的显式同步会影响成本归属。`commit` 包含 GDN 前缀
恢复、hidden taps 历史更新、draft 上下文组合／投影／安装和事务提交，不能将
整段约 47 秒直接等同于 recurrent-state 恢复成本。下一次优化前应进一步拆分。

### 关闭细分 profiling 的控制配对

运行 ID：`c4_tasks4096_noprofile_r0_20261007`。使用相同源码、输入、K=7、
验证块长 4、固定微批 4、显存追踪与轻量统计；仅移除
`--profile-dflash2-stages`。顺序为 target → DFlash2。该额外配对用来检查
显式同步引入的测量开销，不与前三轮混合计算均值或声称它本身具有三轮重复性。
控制结果：target-only **37.7223 tok/s**，DFlash2 **33.7303 tok/s**，吞吐比
**0.8942**（低约 10.6%）；总耗时分别为 434.332／485.735 秒。
4/4 请求、16,384/16,384 token 严格一致，且输出哈希、接受数与接受分布
都与前三轮一致，均无提前 EOS。manifest 比较证实只有 run ID 与
`profile_dflash2_stages` 从 true 改为 false；源码树相同。

控制配对 target decode 375.026 秒，DFlash2 verify 352.442 秒、proposal
27.463 秒、commit 46.384 秒、sample 0.022 秒。解码吞吐分别为43.677和
38.423 tok/s，比值0.8797。TTFT p50为58.326／59.080秒；TPOT p50为
91.821／101.034毫秒，p99为91.821／104.105毫秒。峰值分配显存分别为
54.821／59.490 GiB；紧凑更新记录峰值仍170,164,224 bytes，完整逐位置快照0。

对比前三轮均值，此轮 target 吞吐高0.25%，DFlash2低0.32%；这一次控制
没有观察到关闭同步 profiling 的端到端收益，也未扭转负收益结论。
**不能据此声称 profiling 开销为零**，或将一轮控制冒充三轮无 profiling 复测。
保持其余阶段成本不变，控制配对 decode 持平要求 verify 从352.442秒降至
约301.157秒（约14.6%）；也可通过共同降低 proposal／commit 达到同样的总预算。

合计四组配对 **16/16 请求、65,536/65,536 输出 token** 严格一致，
所有运行对应请求的输出哈希相同。当前证据支持继续优化执行成本，
不支持宣称稳定端到端加速。

### 后续优化顺序

1. 关闭细分 profiling 的控制已完成，未扭转负收益；后续吞吐验收默认关闭
   细分同步 profiling，必要的诊断运行与最终性能复测分开报告。
2. 在融合 GDN 后重新对照 4-token 分块与完整 8-token 验证块。当前每轮
   1345 个投机 engine 周期仍需 2183 次模型块调用；整块可能减少权重读取，
   但会多算拒绝后的后缀，必须实测，不能套用融合前短负载结论。
3. 细分 `commit` 的前缀恢复、上下文历史和投影成本，再决定是否融合紧凑
   GDN 前缀恢复及合批上下文投影。继续保留固定数值形状、回滚与逐 token 验收，
   不恢复 O(batch×K) 完整状态快照。
4. 候选方案先 C4 同输入配对验证，再做三轮长输出复测与 C8。TP=2／C16／C32
   尚未在本轮实现或验证；当前服务器只有一张 A800。
